# 硬性规则（MUST）
- 修改代码前先给思路，等确认。方案级变化更新到 Implementation Plan
- 任何不确定 —— 假设、歧义、代码矛盾 —— 一律停下提问，不要猜
- NEVER 把密钥写进代码，走 .env 或环境变量
- 数据库/表改动必须同时给运行脚本和回滚脚本，由人工执行，不得自己执行
- 新增用户可见文本一律走多语言资源（页面标签、校验注解、Controller/BLL 提示、JS 弹窗）
- C#/视图/JS 文件写入后必须是 UTF-8 with BOM（编辑工具会静默剥离，导致 Windows 下乱码）；SQL 脚本除外
- 存储过程等 SQL 尽量用通用语法，保留迁移到 MySQL 的余地
- 提示显示、页面跳转、异常处理复用框架现有机制；不做与本次任务无关的改动
- 阶段性改动完成后，总结修改内容和经验，写入相关的changelog的md文件

# 终端命令约束
- 每次只执行一条命令，禁止 `;` `&&` `||` `|` 串联
- 长时间命令（构建/测试/还原包）执行前说明预计耗时，超 15 分钟无输出主动中断

# 测试编写规范
- ALWAYS 编写测试用例时只修改 HROneTime.Tests/ 和 HROneTime.UITests/ 两个目录下的文件。确需改动这两个目录以外的文件（.sln、AssemblyInfo、被测类可测试性调整）时，必须先说明原因和范围，等待确认
- ALWAYS UT，API，UI等层级，所有的测试用例中编写的断言不要增加兜底判断，必须严格匹配预期的错误代码或具体错误信息，避免初略比对，避免try catch吞没异常，减少假阳性判断

# 代码风格
- 严格匹配项目现有风格；既有文件超限不主动重构
- 新增代码单文件 ≤300 行（测试除外），单方法 ≤100 行
- 优先复用项目已有实现，不为一次性需求造抽象层
