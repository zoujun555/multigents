## 允许改动的范围

只能改测试相关的文件：{{test_paths}}，以及 `{{req_dir}}`。**不要修改产品代码。**

## 要做的事

1. 先看仓库里已有的测试是否已经覆盖了本需求的验收标准。已有用例足够时不要重复写，在 test-design.md 里指出是哪些用例。
2. 对没有覆盖的验收标准和测试要点设计用例：正常流程、边界值、错误输入、权限。
3. 用仓库现有的测试框架实现，放在允许的目录里，风格与现有测试一致。
4. 按下面的命令构建，确认测试代码能编译。可以运行不依赖被测应用和数据库的纯单元测试。

## 产出

写 `{{req_dir}}test-design.md`，第一行是：

- `RESULT: PASS`：测试已就绪（新写的或已有的），测试代码能编译，可以进入集成运行。
- `RESULT: BLOCKED`：信息或环境不足，无法完成。

之后写：

- **用例清单**：编号、对应的验收标准、测什么、是新增还是已有、所在文件。
- **集成运行时要跑哪些用例**：给出过滤条件或用例名，供下一阶段使用。
- **没有覆盖的**：哪些情况没有用例，为什么。

## 通用规则

- 你在无头模式下运行，没有人能回答提问。遇到必须由人决定的事，不要猜：把问题写进本阶段的结果文件，标记为 BLOCKED，然后结束。
- 只在当前目录（本需求的 Git 工作树）内读写，不要碰目录外的任何文件。
- 不要执行 `git commit`、`git push`、`git checkout`、`git merge`，不要切换分支。提交由工作台在你结束后统一完成。
- 不要安装全局工具，不要改系统设置，不要读取任何凭据或密钥文件。
- 结果文件用中文写，第一行必须是规定的标记行（工作台靠它判断下一步）。
