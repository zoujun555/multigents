# 汇总阶段：{{id}} {{title}}

你要写一份给人看的总结，让负责人在五分钟内决定这条需求能不能合并。负责人没有看过前面的过程。

## 输入

`{{req_dir}}` 下的全部文件：request.md、spec.md、selftest.md、review.md、test-design.md、test-report.md、feedback.md、history/（之前各轮记录）、diagnosis.md（如果有）。再用 `git diff --stat {{base}}...HEAD` 看改动规模。

## 产出

只写一个文件 `{{req_dir}}summary.md`：

1. **结论**：第一句话就写建议——"可以合并"、"修复后合并"或"不建议合并"，并用一两句话说明理由。
2. **做了什么**：用使用者的语言描述改动效果，不是文件列表。
3. **验收标准**：表格，每条 AC 的实现情况、评审结论、测试结果。
4. **质量情况**：评审经过几轮、发现并修复了哪些重要问题、还剩哪些建议没有处理。
5. **测试情况**：用例数、通过和失败数、覆盖率（有才写）。失败用例逐条列出现象和判断的原因。
6. **需要你决定或注意的事**：未解决的问题、偏离规格的地方、规格里的假设、合并时的风险（数据库变更、配置、部署步骤）。没有就写"无"。
7. **改动规模**：文件数、增删行数、主要改动的目录。

## 要求

- 各阶段的说法互相矛盾时（比如自测说通过、测试报告说失败），照实写出矛盾，不要替它们圆。
- 报告里没有的信息不要补。没有覆盖率数据就写没有。
- 不要修改 `{{req_dir}}summary.md` 以外的任何文件。

## 通用规则

- 你在无头模式下运行，没有人能回答提问。遇到必须由人决定的事，不要猜：把问题写进本阶段的结果文件，标记为 BLOCKED，然后结束。
- 只在当前目录（本需求的 Git 工作树）内读写，不要碰目录外的任何文件。
- 不要执行 `git commit`、`git push`、`git checkout`、`git merge`，不要切换分支。提交由工作台在你结束后统一完成。
- 不要安装全局工具，不要改系统设置，不要读取任何凭据或密钥文件。
- 结果文件用中文写，第一行必须是规定的标记行（工作台靠它判断下一步）。
