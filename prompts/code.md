## 输入

- `{{req_dir}}spec.md`：已批准的规格，以它为准。
- `{{req_dir}}request.md`：需求原文，仅供理解背景。
- `{{req_dir}}feedback.md`（如果存在）：只看标题含「批准规格时附带的意见」的部分，那是负责人批准规格时的补充要求，和规格同等重要，要照做；与规格冲突时以规格为准，并在 selftest.md 里指出。其余部分是早先被退回的意见，已经被规格吸收，不用再处理。

## 要做的事

1. 实现 spec。spec 规定的是决策、契约和验收标准，不是修改清单：
   - spec 写明的决策和契约必须照做。你认为某条决策行不通或有错时，不要自行改掉：写 `RESULT: BLOCKED` 并说明原因。
   - spec 没有规定的（改哪些文件、怎么组织代码、清单里没列全的条目），由你决定。沿用仓库现有的做法，选最直接简单的实现。spec 只给了规则和例子的清单，由你按规则补全。
   - 只做 spec 范围内的改动，不要顺手重构无关代码。spec 开头的「给负责人的摘要」是概述，细节以后面各节为准。
2. 按下面"构建和验证"一节的命令构建。
3. 按同一节的命令运行现有单元测试。你的改动不能让原来通过的测试失败。
4. 为新逻辑补最基本的单元测试（如果仓库已有单元测试的做法）。完整的自动化测试由后面的测试阶段负责，这里不用做全。
5. 对照 spec 的每条验收标准自查。

## 产出

写 `{{req_dir}}selftest.md`，第一行是下面三者之一：

- `RESULT: PASS`：构建通过，现有测试通过，验收标准都已实现。
- `RESULT: FAIL`：尽力后仍有构建或测试失败。
- `RESULT: BLOCKED`：缺少必须由人提供的信息或环境。

之后写：改了哪些文件（每个一句话说明）、构建命令和结果、测试命令和结果（通过/失败数量）、每条验收标准的实现情况、spec 没有规定而由你决定的主要实现选择（每条一句话，供评审者核对）、偏离 spec 的地方及原因、遗留问题。

## 通用规则

- 你在无头模式下运行，没有人能回答提问。遇到必须由人决定的事，不要猜：把问题写进本阶段的结果文件，标记为 BLOCKED，然后结束。

- 不要安装全局工具，不要改系统设置，不要读取任何凭据或密钥文件。
